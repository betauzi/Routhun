# รู้ทัน (Routhun)

**ต้นแบบระบบจัดการและเปิดเผยเส้นทางเงินบริจาคของมูลนิธิ** — ตั้งแต่เงินเข้าบัญชีมูลนิธิ การจัดสรรเข้าโครงการ รายจ่ายและการอนุมัติ ไปจนถึงการตรวจความคงเดิมของข้อมูลด้วย Merkle proof และ *ทางเลือก* ในการยึด Merkle root บน Ethereum

> **สถานะโครงการ:** ระบบสาธิตด้วยข้อมูลสมมติ ไม่ใช่ช่องทางรับเงิน ไม่ใช่งบที่ผู้สอบบัญชีรับรอง **ยังไม่เชื่อมรายการธนาคารจริง และยังไม่ได้ยึดข้อมูลขึ้น Ethereum จริง** อย่าใช้ข้อมูลในเดโมเพื่อยืนยันการบริจาคหรือค่าใช้จ่ายจริง

## ปัญหาที่ต้องการแก้

หลังโอนเงินผ่าน QR พร้อมเพย์เข้าบัญชีมูลนิธิ ผู้บริจาคมักเห็นเพียงสลิป แต่ไม่รู้จากข้อมูลที่ตรวจสอบได้ว่า **มูลนิธิรับเงินแล้วหรือยัง จัดสรรเข้ากองกลางหรือโครงการใด และโครงการมีรายจ่ายที่อนุมัติแล้วเท่าไร** ฝั่งมูลนิธิเองก็ต้องรวบรวมรายการธนาคาร บัญชี หลักฐานรายจ่าย และการอนุมัติจากหลายขั้นตอน ส่วนผู้ตรวจสอบต้องแยกว่า “ข้อมูลที่แสดงตรงกับข้อมูลที่เคยบันทึก” กับ “ข้อมูลต้นทางเป็นความจริง” ซึ่งไม่ใช่เรื่องเดียวกัน

รู้ทันจึงแยกงานออกเป็น 3 ชั้น:

1. **บันทึกและกำกับเงิน:** เชื่อมรายการเงินเข้ากับบัญชีของมูลนิธิ บันทึกการจัดสรร รายจ่าย และการอนุมัติ พร้อมแยกข้อมูลตามมูลนิธิ
2. **อธิบายให้คนทั่วไปเข้าใจ:** ผู้บริจาคใช้เลขธุรกรรมบนสลิปและยอดเงินเพื่อค้นรายการที่มูลนิธิบันทึกไว้ รับรหัสติดตาม แล้วดูยอดรับ ยอดจัดสรร และยอดคงเหลือที่ยังไม่ได้จัดสรร
3. **ตรวจความคงเดิม:** คำนวณ hash/Merkle proof จากข้อมูลบัญชี และออกแบบให้ยึดเพียง root ต่อรอบลง smart contract เมื่อมีการตั้งค่าและตรวจธุรกรรมจริง

**ข้อจำกัดที่ต้องพูดตรง ๆ:** เงินเข้าบัญชีรวมไม่ได้ติดป้ายว่า “ธนบัตร 100 บาทของคนนี้จ่ายใบเสร็จใบไหน” ระบบจึงแสดง **การจัดสรรเงินบริจาคเข้าสู่โครงการ** และ **ยอดรายจ่ายรวมของโครงการที่อนุมัติแล้ว** ไม่อ้างว่ารายจ่ายรายการหนึ่งใช้เงินของผู้บริจาคคนนั้นโดยตรง

## ภาพรวมการทำงาน: Input → Process → Output

```text
ผู้บริจาค ──โอนเงินบาทผ่าน QR/ธนาคาร──> บัญชีธนาคารของมูลนิธิ
                                             │
                    ข้อมูลรายการเงินเข้า* ───┤
                                             ▼
                                   จับคู่ธุรกรรมและบันทึกบัญชีคู่
                                             │
                     ┌───────────────────────┼────────────────────────┐
                     ▼                       ▼                        ▼
           ออกรหัสติดตาม               จัดสรรเข้ากองทุน           รายจ่าย + หลักฐาน
           (หลังจับคู่เงินเข้า)          / โครงการ                   ↓
                     │                       │                 กรรมการสองบัญชีอนุมัติ
                     └───────────────────────┼────────────────────────┘
                                             ▼
                           สถานะผู้บริจาค / รายงาน / ข้อมูลสาธารณะ
                                             │
                            journal → SHA-256 → Merkle tree → root
                                             │
                           proof ในเครื่อง ──┴──> Ethereum* (เฉพาะ root)
```

`*` ในเดโม ข้อมูลธนาคารเป็น **รายการสมมติ** ที่ระบบสร้างไว้/เจ้าหน้าที่เพิ่มได้; Ethereum ยังเป็น **โค้ดเตรียมเชื่อมต่อ** ไม่ใช่ธุรกรรมจริง

### ผู้บริจาคตรวจอะไรได้

- เลือกมูลนิธิ กรอก **เลขธุรกรรมบนสลิป + ยอดเงิน** ไม่ต้องกรอกชื่อ–นามสกุลหรือเผยสลิปต่อสาธารณะ ระบบจะออกรหัสติดตามก็ต่อเมื่อพบรายการ **เงินเข้า** ที่จับคู่กับ donation journal ของมูลนิธินั้นแล้ว
- รหัสติดตามแบบสุ่มใช้เปิดยอดบริจาค การจัดสรรตามโครงการ และยอดที่ยังไม่จัดสรร; หากยังไม่พบเงินเข้าจะแจ้งว่า **ยังยืนยันไม่ได้** ไม่ถือว่าสลิปที่ส่งมาเป็นหลักฐานเงินเข้าโดยลำพัง
- หน้าสาธารณะแสดงยอดรวมของมูลนิธิและให้ค้นเลขอ้างอิงที่ผู้ใช้มีเอง **ไม่แจกแจงเลขธุรกรรม/ยอดเงินรายคน** เพื่อไม่ให้คนอื่นนำไปอ้างรับรหัสติดตาม
- การมีเลขธุรกรรมกับยอดเงิน **ยังไม่พิสูจน์ว่าคนกรอกเป็นเจ้าของสลิป** ฟีเจอร์นี้จึงยังไม่พร้อมใช้กับข้อมูลผู้บริจาคจริงโดยไม่มีขั้นตอนยืนยันสิทธิ์เพิ่มเติม

### เจ้าหน้าที่ กรรมการ และผู้สอบบัญชี

| บทบาท | งานหลักในต้นแบบ |
|---|---|
| เจ้าหน้าที่ | บันทึกรายการธนาคารจำลอง (เฉพาะเดโม), จัดสรรเงินเข้าตามโครงการ, ส่งรายจ่ายพร้อมไฟล์หลักฐาน |
| กรรมการ | พิจารณารายจ่าย; ต้องมี **สองบัญชีกรรมการต่างกัน** อนุมัติก่อนสร้างรายการรายจ่ายลงสมุดบัญชี |
| ผู้สอบบัญชี | อ่านสมุดบัญชี รายจ่าย หลักฐาน รายงาน และประวัติการทำงานตามสิทธิ์; **ไม่ได้เท่ากับรับรองงบ** |
| ผู้ดูแล | จัดการผู้ใช้/การเผยแพร่หน้าสาธารณะ ดูข้อมูลขององค์กร และสั่งสร้างรอบหลักฐานด้วยมือ |
| ผู้เยี่ยมชม | ดูข้อมูลรวม ค้นข้อมูลที่มีเลขอ้างอิงของตน และติดตามเงินด้วยรหัส โดยไม่ต้องล็อกอิน |

เมนูของแต่ละบทบาทซ่อนหน้าที่ไม่เกี่ยวข้องเพื่อให้ง่ายต่อการใช้; **การตรวจสิทธิ์จริงอยู่ที่ API** และ query จำกัดข้อมูลตามองค์กร ไม่ใช่อาศัยแค่การซ่อนปุ่ม

## Ethereum อยู่ตรงไหน และช่วยอะไร

**ผู้บริจาคโอนเงินบาทเข้าบัญชีมูลนิธิโดยตรง ไม่ต้องถือ ETH หรือมีกระเป๋า Ethereum** รู้ทันไม่รับเงินเป็นตัวกลาง และไม่บันทึกชื่อ สลิป ไฟล์ใบเสร็จ หรือยอดรายบุคคลลงเชน

ระบบคำนวณ SHA-256 ของรายการบัญชีในรูปแบบคงที่ นำ hash หลายรายการมารวมเป็น **Merkle tree** แล้วได้ **Merkle root** หนึ่งค่าต่อรอบ โค้ด Solidity [`contracts/RouthunAnchor.sol`](contracts/RouthunAnchor.sol) ออกแบบให้ owner ยึด root ต่อ batch ได้ **ครั้งเดียว**; ฝั่ง [`server/chain.mjs`](server/chain.mjs) เตรียมอ่าน root ผ่าน RPC ส่งธุรกรรมเมื่อเปิดใช้งาน และรอ receipt ก่อนรายงานว่ายืนยันแล้ว Smart contract เป็นโปรแกรมและ state บน Ethereum; การเขียน state ต้องส่งธุรกรรมซึ่งมีค่า gas.[1][2][3]

แอปอ่านข้อมูลและส่งธุรกรรมผ่าน JSON-RPC ของ execution client ได้.[4]

**ทำไมไม่เก็บทุกใบเสร็จบนเชน?** เพื่อไม่เผยแพร่ข้อมูลส่วนบุคคล/ไฟล์ละเอียดต่อสาธารณะและไม่ต้องเขียนข้อมูลจำนวนมากเป็นธุรกรรมมีค่าใช้จ่าย เอกสารหลักฐานเก็บนอกเชนแบบเข้ารหัส; บนเชนมีเพียง root สำหรับนำไปเทียบความคงเดิมในอนาคต

```text
ข้อมูลบัญชี → leaf hash → Merkle proof → root ของรอบ
                                         │
                       [โหมดเดโม: root ในฐานข้อมูลเท่านั้น]
                                         │
                       [เมื่อเปิดเชนจริง: เทียบกับ rootOf(batchKey) บน Ethereum]
```

- **ตรวจในเครื่อง (LOCAL ONLY):** ตรวจว่ารายการกับ Merkle path คำนวณกลับไปหา root ที่ระบบให้มาได้ แต่ถ้า root ยังไม่ได้ยึดกับแหล่งอิสระ ผู้ดูแลระบบอาจสร้างชุดข้อมูลและ root ชุดใหม่ได้
- **ยืนยันบนเชน (ON-CHAIN):** จะใช้คำนี้ได้ก็ต่อเมื่อมีการส่งธุรกรรมจริง รอผลสำเร็จ และอ่าน root จากสัญญามาเทียบตรงกัน; ต้นแบบปัจจุบัน **ยังไม่มีธุรกรรมดังกล่าว**
- **สิ่งที่ Ethereum ไม่รับรอง:** ไม่ยืนยันว่าเงินเข้าธนาคารจริง รายจ่ายถูกต้อง สิ่งของถึงผู้รับ หรือผู้สอบบัญชีรับรองงบ — สิ่งเหล่านี้ต้องมีข้อมูลต้นทาง การกำกับดูแล และการตรวจสอบนอกเชน

**หมายเหตุเทคนิค:** Merkle tree ที่แอปสร้างจาก `journals` ไม่ใช่ Ethereum state trie; root ของแอปเป็นค่า SHA-256 และ `batchKey` คำนวณจาก batch ID ด้วย Keccak-256 ใน adapter

## ลองใช้ในเครื่อง

ใช้ Node.js ที่รองรับ `node:sqlite` และติดตั้ง dependencies จากโฟลเดอร์โปรเจกต์:

```bash
npm install
npm run dev
```

เปิด `http://127.0.0.1:5173` (หน้าเว็บ) หรือ `http://localhost:5173`; API ใช้พอร์ต `3001` โดยค่าเริ่มต้น **ไม่ต้อง** เปลี่ยน path ในคำสั่งตามตำแหน่งโฟลเดอร์ของคนเขียน README โหมดเดโมสร้างฐานข้อมูลใน `data/routhun.db` และคีย์ไฟล์ตัวอย่างใน `data/`; โฟลเดอร์นี้ถูก ignore จาก Git

**บัญชีเดโมของมูลนิธิแสงใหม่:** `admin@demo.routhun.test`, `staff@demo.routhun.test`, `board1@demo.routhun.test`, `board2@demo.routhun.test`, `auditor@demo.routhun.test` ใช้รหัส `RouthunDemo2027!` เหมือนกัน **ห้ามเปิดบริการเดโมนี้บนอินเทอร์เน็ต**

### ลองติดตามเงินบริจาค

1. เปิด **ติดตามเงินบริจาค** ไม่ต้องล็อกอิน เลือก **มูลนิธิแสงใหม่** กดดูกรณีตัวอย่างเพื่อสำรวจสถานะโดย **ไม่รับสิทธิ์รายการนั้น**; หรือกรอกเลขธุรกรรมสมมติ `DEMO-IN-002` ยอด `500` บาท แล้วกด **ยืนยันกับรายการเงินเข้า** เพื่อออกรหัสติดตาม (รายการหนึ่งออกได้ครั้งเดียว)
2. คัดลอกรหัสติดตามไว้ และกลับมาใส่ที่ช่อง **เคยรับรหัสแล้ว** เพื่อดูยอดที่ยังไม่จัดสรร/ที่จัดสรรแล้ว หากรายการถูกอ้างรับไปก่อน จะออกรหัสใหม่ไม่ได้ และตอนนี้ยังไม่มีกระบวนการกู้รหัส
3. สำหรับกรณี **100 บาท** ให้เจ้าหน้าที่/ผู้ดูแลเพิ่มรายการเงินเข้าทดลองที่เมนู **รายการธนาคาร** แล้วนำเลขอ้างอิงที่ได้กับยอด 100 บาทมาลองกรอกในหน้าผู้บริจาค; เจ้าหน้าที่สามารถจัดสรรรายการนั้นที่เมนู **จัดสรรเงินบริจาค**
4. เดโมมีมูลนิธิและกรณีสมมติหลายแบบ เช่น จัดสรรครบ จัดสรรบางส่วน ยังไม่จัดสรร แบ่งสองโครงการ รายจ่ายอนุมัติ/รออนุมัติ/ถูกปฏิเสธ และรายการเงินเข้าที่ยังไม่จับคู่; **การกดดูตัวอย่าง** เป็นภาพจำลองที่เปิดซ้ำได้ ไม่ใช่การรับเงินของตัวเอง

บัญชีเดโมของมูลนิธิอื่นเป็นข้อมูลทดสอบแยก tenant; รายชื่อบัญชีบนหน้า login แสดงเฉพาะมูลนิธิแสงใหม่เพื่อลดความสับสน ฐานข้อมูลจริงของผู้ใช้งานไม่ควรใช้รหัสผ่านเดโม

### ตรวจ Merkle proof

ล็อกอินเป็นผู้ดูแล เปิด **ตรวจหลักฐาน** สร้างรอบหลักฐานจากรายการที่ยังไม่จัดรอบ แล้วค้น `RT-DEMO-IN-001` ดาวน์โหลด JSON และลองตรวจแยกจากเว็บ:

```bash
node server/verify-proof.mjs path/to/proof.json
```

หากยังไม่ตั้งค่า Ethereum คำสั่งจะรายงานผล `local` เท่านั้น ไม่ได้ตรวจ root บนเชน

| [`server/chain.mjs`](server/chain.mjs), [`contracts/RouthunAnchor.sol`](contracts/RouthunAnchor.sol) | adapter สำหรับ Ethereum และสัญญายึด root (ยังไม่ deploy) |
| [`server/tests/`](server/tests/), [`scripts/`](scripts/) | การทดสอบ API/ข้อมูลสมมติ และ browser E2E |
| [`DEPLOYMENT.md`](DEPLOYMENT.md), [`vercel.mjs`](vercel.mjs) | แนวทางแยก frontend บน Vercel กับ backend ที่มีข้อมูลถาวร |

ยอดเงินในฐานข้อมูลเก็บเป็น **สตางค์จำนวนเต็ม**. ไฟล์หลักฐานที่อัปโหลดผ่านขั้นตอนปกติถูกเข้ารหัส AES-256-GCM; **รายจ่ายที่ seed สำหรับเดโมหลายกรณีไม่มีไฟล์หลักฐานจริง** จึงห้ามอ้างว่าเป็นใบเสร็จที่ตรวจได้

## เตรียมนำขึ้น Vercel ≠ พร้อมเปิดรับเงินจริง

[`vercel.mjs`](vercel.mjs) เตรียม build หน้า Vite ลง `dist/` และ rewrite `/api/*` ไปยัง **Express backend ที่โฮสต์แยกบนระบบที่มี storage ถาวร** ต้องกำหนด `BACKEND_ORIGIN` (HTTPS) บน Vercel และ `PUBLIC_ORIGIN` (โดเมนหน้าเว็บ) บน backend อ่านขั้นตอนใน [`DEPLOYMENT.md`](DEPLOYMENT.md) โครงการ **ยังไม่ได้ deploy**; SQLite/ไฟล์หลักฐานไม่ควรไปอยู่บนดิสก์ชั่วคราวของ Vercel Functions

ก่อนใช้เงินจริงยังต้องมีอย่างน้อย:

- ช่องทางนำเข้ารายการเงินเข้าจากธนาคาร/พร้อมเพย์ที่ได้รับอนุญาตและตรวจซ้ำได้; ตอนนี้ไม่มี Bank API หรือการตรวจ QR/slip จริง
- ขั้นตอนพิสูจน์ความเป็นเจ้าของรายการบริจาคที่แข็งแรงกว่าเพียงเลขสลิปกับยอดเงิน, การกู้/เพิกถอนรหัสติดตาม, การป้องกันการอ้างรับซ้ำ และแนวทางข้อมูลส่วนบุคคล
- นโยบายอนุมัติการจัดสรร บัญชีเงินบริจาคระบุวัตถุประสงค์ การแก้ไขรายการด้วยรายการกลับบัญชี การปิดงวด การเปิดเผยหลักฐานที่ลบข้อมูลอ่อนไหว และการตรวจสอบโดยผู้มีวิชาชีพ
- การทดสอบการโจมตี/สิทธิ์ข้ามมูลนิธิ backup/restore, การจัดการคีย์เข้ารหัส, monitoring และการย้ายฐานข้อมูล/ไฟล์หลักฐานไปสู่ระบบถาวรที่รองรับ scale
- การทดสอบและ audit smart contract การจัดการ owner key, gas budget, เครือข่าย/RPC และการทำ job ยึด root แบบทนทาน; ปัจจุบันสร้าง batch ด้วยมือเท่านั้น

**หลักการสำคัญ:** บล็อกเชนเป็น “หมุดอ้างอิงความคงเดิมของข้อมูลที่ถูกบันทึก” ไม่ใช่เครื่องพิสูจน์ความจริงของข้อมูลบัญชีหรือการส่งมอบของมูลนิธิ
